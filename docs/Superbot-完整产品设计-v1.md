# Superbot · 完整产品设计 v1

- 日期：2026-11-04
- 性质：这次不是“再加一个功能”，而是把产品从“插件骨架 + 任务工具”重新定义为**一个能替你当项目经理的 Superbot 界面**，并把需求、拆解、派工、执行、验收、记忆、汇报、分析全部打通。
- 现有 P0 资产保留并升级：`dsh-superbot`（工具/设置/去重）、`task-engine`（契约/状态机/调度）、`session-policy`（轮换/交接）。
- 约束：DSH 插件形态、不改核心、不做独立 App、真实项目落地、所有 AI 动作可审计。

---

## 0. 先回答“我的目标是什么”

你要的不是一个“会聊天的任务面板”，而是一个**像员工一样接活的经理**：

> 你给一个需求 → 它先帮你把需求问清楚、改写成可执行规格 → 拆成有依赖的任务 → 安排 worker 去对应项目里干 → 干完独立验收 → 把结果、进度、风险、要你决定的事汇报给你 → 把这次的经验/决策记进长期记忆 → 下次接着用。

用一句话定义完成：

> **你在一个界面里发需求，剩下的“拆解、派工、执行、验收、记录、汇报、分析”由 Superbot 闭环完成；项目里真的有代码/提交/测试/验收记录，且你随时能看到进展和需要决策的点。**

### 0.1 需求 → 机制对照

| 你的要求 | 产品机制 |
|---|---|
| 一个 Superbot 界面 | 侧栏入口 + 主控制台（聊天/任务/决策/待办/团队/项目/记忆/分析/设置） |
| 像员工一样发配需求和任务 | Requirement Intake → 澄清 → Spec → Plan；聊天里直接说，也可表单 |
| 帮我分配拆解优化需求 | 澄清四问 + 验收标准 + 任务 DAG + 风险/依赖/工作量；计划可编辑 |
| 安排人手去工作 | 按项目创建 worker session；每项目一个写者；模型/工具/preset 按角色分配 |
| 工作了有长线记忆 | 项目记忆/用户偏好/角色关系三层；事件 + 投影；可查/导出/删除 |
| 调度所有任务、结果汇报 | 确定性调度器 + 任务板 + 工作汇报 + 每日/每周 digest |
| 分析任务进度结果 | 度量：完成率、周期、返工、阻塞、注意力、token/成本；趋势和建议 |
| 真正把项目任务落地 | worker 在真实项目 cwd/分支/worktree 执行；验收命令复跑；人工 accept |
| 涉及到的都要想清楚 | 本文件覆盖：对象模型、流程、UI、角色、调度、上下文、记忆、分析、设置、架构、路线、验收、风险 |

## 1. 产品原则（高度）

1. **用户只做决定，不做调度**：需求确认、计划批准、决策回答、结果验收由你；其余由系统推进。
2. **一个前台声音**：默认Superbot；工作结果用专业 work 语域，陪伴/关系用 casual；后台 worker 无角色。
3. **状态外置，上下文可丢**：任务板/事件/记忆是权威；会话只是工作台；短会话 + 交接。
4. **确定性优先**：调度、优先级、验收、权限由代码决定；模型只做理解、拆解、执行、解释。
5. **真实落地**：每个任务必须有验收命令/行为标准；没有证据不算完成；done 只能人按。
6. **注意力预算**：默认安静；只在需要决定/可交付/失败时打扰；一次只问一个问题。
7. **可审计、可回滚**：任务、决策、报告、记忆、工具调用都有记录；危险动作先问。

## 2. 对象模型（系统的事实来源）

```
Project          项目：id/name/root/repo/defaultBranch/配置
Requirement      需求：原始话术 → 澄清后的规格（目标/范围/非目标/约束/验收）
Plan             计划：需求 → 任务 DAG + 假设/风险/估算 + 版本
Task             任务：TaskSpec + 状态 + 依赖 + owner + 尝试 + 验收 + touches
Run/Attempt      一次执行：task + worker session + 起止 + 结果
WorkReport       工作汇报：事实（改动/测试/提交/风险/待办）
Verification     验收：命令证据 + 结论 + 人工接受/返工
Waitpoint        等待：decision / human_action / external，独立于任务状态
Todo             你要做的事（与任务严格分开）
MemoryEntry      记忆：项目/用户/角色关系，带来源、作用域、时效
ProgressSnapshot 进度快照：用于趋势/分析（可重建）
```

### 2.1 任务状态

`draft → todo → in_progress → in_review → done`；`blocked / canceled`。低风险验证通过可由 policy 自动 done（审计+可重开）；高风险/审美类 `done` 只能 human。

### 2.2 等待与决策

- 决策必须有：问题、2–4 个选项、每个选项的后果、默认项、过期时间；
- 过期不静默：进入“待你决定”红区；
- 一次只问一个问题；能批量合并的合并。

### 2.3 项目空间

- 每个 `Project` 绑定真实目录（cwd）、git 仓库、默认分支、测试命令、写权限边界；
- **同一项目同时只允许一个写者**；不同项目可并行；
- worker 的 session cwd 必须是项目根，不能跨项目改文件；
- 文件级锁用 `touches` 声明，冲突任务等待。

## 3. 端到端流程

```
你：一句话需求
  ↓
① Intake：识别项目/目标/约束 → 追问 ≤3 个关键问题
  ↓
② Spec：写成可执行需求（目标/范围/非目标/验收/风险）
  ↓ 你确认（或低风险自动）
③ Plan：拆任务 DAG（10–30 分钟/个）+ 依赖 + 估算 + 模型档位
  ↓ 你批准（或按自动化等级）
④ Dispatch：按项目/优先级/依赖/WIP 派 worker
  ↓
⑤ Execute：worker 在项目目录改代码、跑测试、提交；后台任务
  ↓
⑥ Verify：独立 verifier 跑验收命令；不通过 → 驳回包返工
  ↓
⑦ Report：work 寄存器汇报 + 进度更新 + 待你决定
  ↓
⑧ Memory：抽取项目决策/教训/偏好 → 人可审 → 入库
  ↓
⑨ Analyze：趋势/瓶颈/返工/成本 → 调整计划
```

### 3.1 需求澄清（“深度不是更大”）

Intake 阶段默认问四个高杠杆问题（能回答就跳过，不机械问）：

1. 这个领域顶尖专家会额外做什么？（质量标准）
2. 用什么原始材料/一手信息？（避免二手）
3. 用什么具体方法/工具？（执行路径）
4. 有什么外部标准/验收命令能证明结果对？

产出 `RequirementSpec`，必须包含：目标、范围、非目标、约束、验收、风险、依赖。

### 3.2 拆解与优化

- 按“文件/模块边界”和“可独立验收”拆，不按人天平均切；
- 任务 10–30 分钟；大任务先 epic + 子任务 DAG；
- 每任务写 `touches`（预计修改文件/glob）与 `acceptance`（命令/行为）；
- 计划里显式写假设、风险、需要你决定的分叉；
- 计划版本化，变更留 diff。

### 3.3 派工

- 选择就绪任务（依赖完成、项目空闲、文件不冲突、WIP 未满）；
- 创建 worker session：cwd=项目根、preset=worker、TaskSpec + handoff bundle + 必要文件引用；
- 给每个 worker 明确：改什么、不改什么、怎么验收、禁止命令（checkout/reset/clean、宽泛 git add、自动 merge/push）；
- 失败/超时按策略重试或交回队列，不无限重试。

### 3.4 验收：低风险自动、高风险人工（2026-11-04 更新）

- verifier 是新会话，只拿 TaskSpec + 验收 + diff/提交 + 报告；
- 实际执行验收命令；输出证据；
- 失败 → 驳回包（原因、检查项、证据）全量给下一 worker；
- 通过后按风险分流：

| 情况 | 处理 |
|---|---|
| 验证通过 + 低风险 + 可逆 + 无外部副作用 + 无主观/审美标签 | **policy 自动通过**（记录 `acceptedBy: "policy"`、原因、证据；可复核/重开） |
| 审美/设计/UX/文案/语气/风格等主观项 | **必须人看** |
| 高风险、不可逆、外部副作用、安全/权限/凭据、数据模型/迁移/公开 API/发布 | **必须人看** |
| 验收未通过/证据缺失/分类不确定 | **必须人看** |

- “完成”不再等于“只有人按”：低风险任务可由策略自动 done，但必须留下审计、可一键重开；高风险和审美类永远到人。
- 判定由 `classifyAcceptance` 纯函数做，标签/风险可由任务声明和模型建议，但**默认可疑就从人**。

### 3.5 汇报

- 单任务：结论 / 改动 / 验证 / 风险 / 下一步；
- 需求级：完成了什么、还剩什么、需要你决定什么；
- 每日/每周：进度、阻塞、决策、成本、建议；
- 用户不打开时：只在“需要决定/可验收/失败”通知。

## 4. 界面设计（一个 Superbot 控制台）

### 4.1 布局

```
┌ Superbot ─────────────────────────────────────────────┐
│ [今日] [任务] [待你决定] [待办] [团队] [项目] [记忆] [分析] [设置] │
├──────────────┬──────────────────────────────┬──────────────┤
│ 项目/任务列表 │ 主区域：对话 / 任务详情 / 计划  │ 右侧：worker  │
│ 今日/活跃/等待 │ 验收证据 / 进度时间线 / 决策    │ 决策队列/记忆 │
└──────────────┴──────────────────────────────┴──────────────┘
```

- 左侧：项目树 + 任务视图（今日/活跃/等待/待你决定/完成/归档）；
- 主区：默认是和Superbot对话；点任务切详情；点计划看 DAG；
- 右侧：worker 状态、待你决定、记忆命中；
- 顶部全局：自动化等级、预算、角色切换、暂停。

### 4.2 关键页面

1. **今日**：今天要推进什么、需要你决定什么、worker 在干什么、风险；
2. **任务**：看板/列表；卡片显示状态、优先级、所有者、进度来源、验收；
3. **待你决定**：一次一题，选项+后果+默认+过期；回答后任务继续；
4. **待办**：你要做的事（与任务分开），支持提醒/等待外部；
5. **团队**：每个 worker 的 session、任务、状态、耗时、token；可打开会话；
6. **项目**：项目根目录、分支、最近提交、健康度、配置；
7. **记忆**：项目决策/偏好/关系摘要；可查、改、删、导出；来源可点；
8. **分析**：完成率、周期、返工、阻塞时间、token/成本、趋势、建议；
9. **设置**：角色、自动化等级、模型路由、预算、上下文阈值、通知、项目、数据。

### 4.3 交互原则

- 任何“完成”都要有证据；任何“等待”都要说等谁/等什么；
- 进度标注来源（命令/事件/自报/时间基线），不伪造百分比；
- 计划/规格可编辑，保存版本；
- 一键：批准计划、回答决策、接受/返工、暂停/恢复、打开 worker 会话。

## 5. 角色与 Agent 架构

```
用户
  ↕
Manager（Superbot，前台，人格层）
  ├─ Intake/Clarify（理解需求、问关键问题）
  ├─ Planner（拆解、DAG、验收、风险）
  ├─ Dispatcher（确定性调度 + 创建 worker）
  ├─ Reporter（work 汇报 / casual 陪伴）
  └─ Memory Curator（候选记忆 → 人审 → 入库）
        ↓
Worker（无角色，任务级，项目 cwd）
        ↓
Verifier（新会话，只读验收）
        ↓
Analyst（度量/趋势/建议，可确定性 + 模型解释）
```

| 角色 | 形态 | 工具 | 上下文 |
|---|---|---|---|
| Manager | agent preset `superbot` | requirement/plan/task/dispatch/decision/report/memory + 只读查询 | 小：任务摘要/决策/报告，不拿执行日志 |
| Worker | preset `superbot-worker` | 工程工具（bash/fs/search/jobs/skills），无 dispatch/team | 只拿 TaskSpec+handoff+文件引用 |
| Verifier | preset `superbot-verifier` | 只读 + 验收命令 + diff | 新会话，不拿 worker 自辩 |
| Memory Curator | 确定性服务 + 可选模型 | 读写记忆（人审） | 事件/报告摘要 |
| Analyst | 确定性指标 + Manager 渲染 | 只读 | 聚合数据 |

**硬边界**：worker/verifier 不注入角色文本；manager 不替 worker 写代码；done 只能人。

## 6. 调度与项目落地

### 6.1 项目注册表

```json
{
  "id": "proj-a",
  "name": "Superbot项目",
  "root": "/Users/…/projects/proj-a",
  "repo": "git@…",
  "defaultBranch": "main",
  "testCommand": "pnpm test",
  "writePolicy": "workspace-write",
  "maxWorkers": 2
}
```

- 新项目通过设置/界面注册；worker 只能在该 root 内操作；
- 每个项目一个写者；跨项目并行；
- 分支/提交策略：任务分支 `agent/t-*`，只精确 `git add`，不自动 push/merge；是否推送由配置决定。

### 6.2 调度算法

1. 过滤 ready（依赖 done、项目空、文件不冲突）；
2. 排序：优先级 → 截止期 → 等待时间 → id；
3. 取到 `maxWorkers`（全局）+ 项目 `maxWorkers`；
4. 给人留一个额外槽；
5. 失败/超时回队列；重试有上限；超限 → 显式“需人处理”终态；
6. 等待人工不占执行槽；超时由调度器统一扫。

### 6.3 Worker 生命周期

- 创建：cwd=项目 root、preset=worker、TaskSpec+handoff、权限/禁止命令；
- 执行：改文件/跑测试/后台任务；turn 结束仍有后台任务时占槽；
- 汇报：`task_report` 提交 WorkReport；
- 结束：success → in_review；failure → 回队列/交人；超时 → 中断+回收；
- 交接：新 worker 拿完整 TaskSpec + handoff bundle + 文件引用，不拿旧会话全文。

## 7. 上下文与长会话策略

### 7.1 会话拓扑

- Manager：长会话但上下文预算小（任务摘要/决策/报告）；
- Worker：短，单任务；warm session 按项目/阶段复用，到预算/边界轮换；
- Verifier：新会话；
- Memory adapter：只读查询。

### 7.2 预算与轮换

- 交互档 120–200k；批量档 300k+（校准实验：到 26 万 token 质量未降，成本约 17×）；
- 70% 建议压缩（官方 compaction+pruner），90% 或任务边界交接；
- 压缩 ≥2 次、上下文污染/跑偏 → 换会话；
- 常驻段稳定（缓存友好），易变状态不进 system prompt。

### 7.3 交接 bundle（不是只有 5 行）

```json
{
  "task": { "id": "t-12", "title": "...", "projectId": "proj-a", "acceptance": ["pnpm test"] },
  "status": "核心函数完成，CLI 未开始",
  "files": ["src/core.py:1-120"],
  "commits": ["abc123"],
  "tests": [{"cmd": "pytest -q", "result": "6 passed"}],
  "decisions": ["store=tasks.json", "priority=low/normal/high"],
  "blockers": ["等用户确认是否需要迁移旧数据"],
  "next": "实现 tasklite/cli.py",
  "evidence": ["WorkReport:wr-7", "diff:…"]
}
```

新 session 只拿这个 bundle + TaskSpec + 文件引用；旧 session 归档；verifier 独立。

### 7.4 长线记忆（三层）

| 层 | 内容 | 写入 | 读取 |
|---|---|---|---|
| 项目记忆 | 决策、约定、里程碑、坑、验收记录 | worker 报告 → manager 候选 → 人审 | manager 计划/汇报；worker 只拿任务相关引用 |
| 用户记忆 | 偏好、沟通方式、边界、常用项目 | 用户对话 + 确认 | 前台；不注入 worker |
| 角色关系 | 经历/日记/关系摘要 | Superbot（cap 内，只追加） | 仅前台 casual；只读适配 fish/outfit |

- 存储：事件 JSONL + SQLite/JSON 投影；Markdown 可导出；
- 召回：按场景触发、有界注入（首轮快照 + 差分）、可解释；
- 遗忘：项目记忆按容量归档；关系记忆只追加；用户可删/导出；
- 红线：worker/verifier 不写记忆；不自动把猜测升级为长期事实；敏感内容不落盘。

## 8. 汇报与分析

### 8.1 报告类型

- 任务报告：结论/改动/验证/风险/下一步；
- 需求总结：完成/未完成/决策/证据；
- 每日 digest：今天推进/阻塞/待决定/明天计划；
- 项目健康：活跃任务、周期、返工、验收通过率、风险；
- 分析建议：瓶颈、估算偏差、模型/成本建议。

### 8.2 指标

| 维度 | 指标 |
|---|---|
| 交付 | 任务完成率、验收通过率、返工率、周期时间 |
| 进度 | 需求完成度、依赖阻塞时长、等待人工时长 |
| 注意力 | 待决定数量/时长、打扰次数 |
| 成本 | token/任务、未缓存输入、cache 命中、压缩次数 |
| 质量 | 测试覆盖（命令证据）、缺陷/回滚次数 |
| 产能 | worker 利用率、并发槽、项目吞吐 |

分析要能回答：哪类任务最慢、哪类返工最多、哪个项目卡住、模型路由是否合理、下一个瓶颈是什么。

## 9. 设置（Superbot 控制台）

- **角色**：默认Superbot/阿哲/自定义；前台注入；worker 不变；
- **自动化等级**：L0 观察 / L1 本地准备 / L2 低风险自动 / L3 更高自动；默认 L1；
- **模型路由**：manager/worker/verifier 分别选模型与 reasoning 档；
- **项目**：根目录、默认分支、测试命令、并发、写权限；
- **上下文**：预算、压缩/交接阈值、去重开关、原文目录；
- **记忆**：开关、容量、是否人审、导出/清空；
- **通知**：决定/验收/失败/每日摘要；
- **数据**：状态目录、导出/备份/清理；
- **工具**：任务工具开关、worker/verifier 工具面（preset）。

保存后即时生效（能热更新就热更新，否则提示重启）；配置版本化可回滚。

- 每个项目最小权限；worker 不能出项目目录；危险命令拦截；

## 15. 控制平面：多项目集中管理（2026-11-04 修正）

### 15.1 先纠正方向

上一版把“项目注册表、worker session、分支”写得像是**你要维护的东西**，这是偏的。  
你的真实目标是：

> **左边 DSH 里有很多项目/会话，人的精力有限。Superbot 要当一个“中台/控制塔”，集中管理这些项目：它自己发现项目、自己判断需求属于哪个项目/文件、自己分配 session 和任务、自己推进；你只在一个中台看进度、回答决策、审查高风险/审美结果。**

- **集中权力 = 集中决策权与可见性**，不是集中微操；
- 项目、session、分支、worktree 都是**执行资源**，由 Bot 管理；
- 你唯一需要的是：**一个总览 + 一个审查队列 + 一个进度视图**。

### 15.2 两层结构

```
┌──────────────────────────────────────────────┐
│ 控制平面：Superbot 中台                     │
│  - 需求入口（一句话/表单）                     │
│  - 项目组合总览（所有项目健康/活跃/进度）        │
│  - 需求路由：属于哪个项目/哪些文件             │
│  - 计划拆解 + 跨项目组合调度                   │
│  - Session 自动驾驶（创建/轮换/交接，你看不到）  │
│  - 审查队列（只放需要人的：决策/高风险/审美）    │
│  - 汇报/分析/记忆                             │
└──────────────────────┬───────────────────────┘
                       │ 自动派发/回收
┌──────────────────────▼───────────────────────┐
│ 执行平面：现有 DSH 项目 + worker 会话          │
│  项目 A（cwd/仓库/文件）  worker-1            │
│  项目 B                   worker-2            │
│  项目 C                   空闲                │
└──────────────────────────────────────────────┘
```

### 15.3 项目清单：自动发现，不让用户维护

- **DSH Workspace 是唯一事实来源**：项目 = workspace 记录（workspaceId/path/title/sessionIds）；我们不另建注册表；
- 清单只是 DSH workspace registry 的投影缓存，可重建；workspace 增删改后刷新；
- 项目目录沿用 DSH 的存放逻辑（目录选择器 / 用户指定路径 / DSH 默认 workspace），不搬家、不自定义根目录；
- 中台接管现有 session：可列出/读取/归档/继续；新 session 建在对应 workspace 的 cwd 下；
- 你可以“置顶/忽略/合并/改名”，但**不需要手工注册**；
- 中台默认展示所有项目；左侧原始会话列表只作为底层资源，不进入日常操作路径。

### 15.4 需求路由：自动落到项目/文件

1. 你说需求（可带项目名；不带则判断）；
2. 中台根据：项目名/路径/最近活动/关键词/最近任务 → 推断目标项目；
3. 不确定时**只问一次**“是 A 还是 B？”；不让你填表；
4. 进入该项目做规格/拆解；任务 `touches` 标明文件/glob；
5. 没有匹配项目时，才问“新建项目还是选已有？”。

### 15.5 Session 自动驾驶

- 每个任务自动创建 worker session：cwd=对应项目根；
- 同一项目一个写者；跨项目可并行；
- 预算/边界到点自动 handoff、换 session；失败自动重试/回收；
- **你不需要看到/管理 session**；只有点任务详情/“查看执行现场”才展开；
- 分支/worktree 是内部实现细节，默认不出现；需要时在任务详情里可查。

### 15.6 跨项目组合调度

- 全局优先级 + 项目优先级 + 依赖 + WIP 上限 + 你的注意力预算；
- 同一时间只推进有限“活跃项目”，其余排队/休眠；
- 项目冲突（同一文件/同一模块）自动排队；
- 每天只给你一份摘要：推进了什么、卡在哪、要你决定什么、明天建议。

### 15.7 中台 UI（核心）

```
┌ Superbot · 中台 ──────────────────────────────┐
│ 今日重点：3 件事                              │
│  [进行中 8] [待你决定 2] [待验收 1] [阻塞 1]     │
├──────────────────────┬─────────────────────────┤
│ 项目组合               │ 审查队列（唯一注意力入口）  │
│ 项目A ████░ 72% 健康   │ ① 登录页配色，需你选 A/B   │
│ 项目B ██░░░ 35% 阻塞   │ ② 数据迁移方案，高风险      │
│ 项目C █████ 90% 待验收 │ ③ 完成：接口重构，低风险已过 │
│ 项目D 休眠中           │                         │
├──────────────────────┴─────────────────────────┤
│ 今天完成 / 进行中任务 / 明天建议 / 成本与注意力     │
└────────────────────────────────────────────────┘
```

- 默认页面就是“项目组合 + 今日 + 审查队列”；
- 点项目 → 项目内需求/任务/进度；
- 点任务 → 规格/验收/证据/worker 现场；
- 左侧 DSH 原始会话列表：保留，但工作流不依赖它。

### 15.8 “集中权力”的边界

| 集中 | 下放 |
|---|---|
| 需求入口、项目总览、审查队列、进度/分析 | 具体执行：worker 会话、文件修改、测试 |
| 跨项目优先级与资源分配 | 单项目内任务排序（按计划） |
| 高风险/审美/冲突的决策权 | 低风险验收（策略自动） |
| 记忆与复盘 | 日常执行噪声（不打扰你） |

### 15.9 对路线图的修正

| 阶段 | 从“工具”改为“中台” |
|---|---|
| **P1** | 项目自动盘点 + 组合总览 + 审查队列 + 需求→项目路由（先只读） |
| **P2** | Session 自动驾驶 + 跨项目调度 + 任务真落地 + 高风险人工验收 |
| **P3** | 项目/需求级进度分析 + 记忆 + 每日摘要 |
| **P4** | 角色/设置/分发 |

> 分支、worktree、session 名称都不作为你日常管理对象；它们只在“执行现场”里可查。



### 15.10 新项目不是例外，且沿用 DSH 的存放逻辑（2026-11-04 修正）

- **项目 = DSH Workspace**：`ctx.workspaceRegistry` 是唯一事实来源；我们的清单只是投影/缓存，不另建项目注册表；
- 项目目录不搬家、不用我们自定义的 `~/Documents/Projects` 之类的根目录；
- 新项目 = 新建一个 DSH Workspace：路径走 DSH 的目录选择器 / 用户给的绝对路径 / DSH 默认 workspace（`<Documents>/deepseek-harness/default-workspace`）；
- 注册后左栏和中台同时出现；建最小骨架 → 派 project-init session 做整体规划 → 中台把计划摘要给你批准 → 拆解/派工；
- **中台能接管现有 session**：读取/列出/归档/继续 DSH 已有会话；不复制、不搬移；
- 你只和中台对话，不直接和 worker session 对话；session 是内部资源。


### 15.11 Superbot记忆/日志/状态的接入（2026-11-04）

- 复用它的**事件流只追加 + 派生状态 + 日记分离 + 日志打码**纪律；
- 控制平面有自己的工作事件/审计/项目记忆；**不写、不迁移、不复制** fish/outfit/persona 数据；
- 角色层只读适配，仅 manager 注入；worker/verifier 零角色注入；
- 现有「Superbot」设置页保留，新设置页做入口，不合并；
- fish 的“家会话”是角色会话，不进入项目调度。
